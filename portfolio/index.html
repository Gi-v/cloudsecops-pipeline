System Design

5 microservices over Kafka

Event-driven architecture ensures scan results propagate in real-time without tight coupling between services.

Architecture Decision Records
ADR-001 Apache Kafka as event backbone Accepted

Context: Six scanners each produce findings at different rates. Tight coupling between scanners and the policy engine would make scaling and adding new scanners expensive.

Decision: Apache Kafka with topic-per-severity partitioning. Producers decouple entirely from consumers. Consumer groups allow horizontal scaling of the policy engine independently.

Consequences: Adds operational complexity (Kafka broker, ZooKeeper), but eliminates a whole class of race conditions. New scanners ship in hours by adding a producer — no policy engine changes required.

ADR-002 OPA/Rego for policy-as-code Accepted

Context: Compliance rules change frequently. Hard-coding them in Python would require service redeployment for every rule update and made audit trail reasoning difficult.

Decision: Open Policy Agent with Rego policies loaded at runtime. Policies are version-controlled alongside infrastructure code. Conftest validates all policies in CI before merge.

Consequences: Security team can update policies without an engineering deploy cycle. 54 policies across CIS/NIST/ISO 27001 with a shared evidence schema eliminated ~60% redundant control evaluation.

ADR-003 MinIO + SHA-256 for evidence store Accepted

Context: Audit evidence must be tamper-evident. An attacker who compromises the scanner could retroactively alter findings to hide a breach.

Decision: Evidence blobs written to MinIO with SHA-256 content addressing. Hash chain links each finding to its predecessor, making retroactive modification detectable during audit replay.

Consequences: Audit prep time dropped from 18h to 4h because evidence is automatically assembled by the hash chain. Immutability is cryptographic, not just policy-based.

ADR-004 asyncio for cloud resource collection Accepted

Context: AWS, GCP, and Azure resource collection made sequential API calls. A full scan took 42 seconds — too slow for near-real-time compliance monitoring.

Decision: Rewrote all collectors using Python asyncio with TaskGroup batching. API calls for EC2, S3, IAM, and KMS now fan out concurrently under a single asyncio event loop.

Consequences: Scan time dropped from 42s → 4.1s (10× improvement). Memory footprint stayed constant — batching avoids materializing all results at once. No changes to downstream consumers required.

Reflection

What I learned

Technical and professional growth across 12 weeks of production security engineering at ArZens.

01 — Architecture

Event-Driven Design Scales

Kafka's producer/consumer decoupling was the key architectural decision. Adding a new scanner took hours, not days — no changes to existing services required. Loose coupling isn't just a pattern; it's a production multiplier.

02 — Policy

Rego Is Surprisingly Expressive

OPA's declarative model maps perfectly to compliance rule evaluation. Writing 54 policies taught me to think about security intent rather than procedural checks — a mindset shift that improved every policy I wrote after the first ten.

03 — Operations

Secure the Security Tool

Running Checkov against our own Terraform and GitHub Actions configs surfaced 3 misconfigurations in the scanner's own infrastructure. The scanner is also an attack surface — a humbling and important lesson.

04 — Compliance

Frameworks Overlap More Than You Think

CIS, NIST, and ISO 27001 address many identical controls with different vocabularies. Mapping them to a shared evidence schema eliminated ~60% of duplicate control evaluation and made audit prep radically simpler.

05 — Performance

Async Batching Changes Everything

Switching AWS resource collection from sequential API calls to asyncio batching cut discovery time from 42 seconds to 4.1 seconds — a 10× speedup from a single architectural change. Profile before optimizing; the bottleneck is rarely where you assume.

06 — Collaboration

API Contracts First, Code Second

Defining OpenAPI specs before writing service code let frontend and backend teams work in parallel from Week 1. Integration issues dropped to near-zero by the time services first connected — the spec was the contract, not the tests.

Common Questions
Is CloudSecOps production-ready?
Yes. The pipeline was deployed to ArZens' staging and production environments during the internship. All six microservices run containerized in Kubernetes with Helm charts, GitHub Actions CI/CD, and automated pre-merge security scanning.
Which cloud providers does it support?
AWS, GCP, and Azure are fully supported with dedicated collection modules. The architecture is extensible — adding a new provider means writing a collector that publishes to the existing Kafka topic, with zero changes to the policy engine or evidence store.
How does the OPA policy engine work?
Each collected resource is evaluated against 54 Rego policies at runtime. Policies are loaded from a Git-tracked directory — no redeployment needed to update rules. The engine returns a structured violations report with evidence pointers, framework mappings, and remediation guidance.
What makes the audit trail tamper-evident?
Evidence blobs are written to MinIO with SHA-256 content addressing. A hash chain links each finding record to its predecessor — altering any historical finding breaks the chain, which is detected during audit replay. This is cryptographic immutability, not just access control.
Can I use this for my own organization?
The architecture is designed to be self-hosted. The Kafka topic schema, OPA policy interface, and REST API are all documented via OpenAPI specs. Reach out via the contact form if you'd like to discuss adapting it for your environment.
